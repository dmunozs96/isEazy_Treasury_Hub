## 1. What Was Done

### Backend — `backend/app/services/classification/engine.py` (new)

Pure classification logic, no database coupling:

- **`ClassificationResult`** — dataclass holding `category_code`, `source`, `rule_id`, `confidence`
- **`evaluate_rule(rule, movement)`** — evaluates a single rule against a movement; supports all 5 match types:
  - `KEYWORD` — case-insensitive substring in `movement.<field>`
  - `REGEX` — `re.search()` against `movement.<field>`
  - `COUNTERPART_NAME` — substring in `movement.counterpart_name`
  - `AMOUNT_RANGE` — JSON `{"min": X, "max": Y}` bounds check
  - `COMPOSITE` — AND of multiple sub-conditions from JSON array
- **`classify_movement(movement, rules)`** — iterates rules sorted by priority ASC; first match wins; returns `UNCLASSIFIED` if no match
- **`load_active_rules(db)`** — async helper to load all active rules from DB ordered by priority

### Backend — `backend/app/schemas/classification.py` (new)

Pydantic schemas:
- `ClassificationRuleCreate` / `ClassificationRuleUpdate` / `ClassificationRuleResponse`
- `BatchClassifyRequest` — `movement_ids: list[UUID] | None`, `force_reclassify: bool`
- `BatchClassifyResponse` — `processed`, `classified`, `unclassified`, `overrides_preserved`
- `SingleClassifyResponse` — `movement_id`, `category_code`, `rule_id`, `source`

### Backend — `backend/app/routers/classifications.py` (full replacement)

Full API replacing the skeleton:

| Method | Path | Purpose |
|--------|------|---------|
| `GET`    | `/api/v1/classifications/categories`      | Taxonomy list (unchanged) |
| `GET`    | `/api/v1/classifications/rules`            | List all rules |
| `POST`   | `/api/v1/classifications/rules`            | Create rule |
| `PUT`    | `/api/v1/classifications/rules/{id}`       | Update rule (any field) |
| `DELETE` | `/api/v1/classifications/rules/{id}`       | Deactivate rule (soft delete) |
| `POST`   | `/api/v1/classifications/batch`            | Batch classify |

Batch classify logic:
- `movement_ids=null + force_reclassify=false` → classify only unclassified movements
- `force_reclassify=true` → re-classify all, but **skip** MANUAL overrides
- Returns stats: processed / classified / unclassified / overrides_preserved

### Backend — `backend/app/routers/movements.py` (extended)

Added `POST /api/v1/movements/{movement_id}/classify`:
- Triggers rules engine for a single movement
- Preserves MANUAL overrides (returns existing classification unchanged)
- Creates or updates `MovementClassification` row

### `scripts/seed.py` (replaced)

Full rewrite. Now seeds:

1. **Companies** (6 entities — unchanged logic, kept)
2. **Category taxonomy v1.1** — 21 entries:
   - 4 level-1 section headers: OPERATING, INVESTING, FINANCING, INTERNAL
   - 16 level-2 leaf categories (OCF×4, ICF×2, FCF×8, INT×2)
   - 1 standalone UNCLASSIFIED (level=1, no parent)
3. **Classification rules** — 27 rules total:
   - 10 intercompany domestic rules (priority 5) — one per company keyword
   - 17 standard treasury rules (priority 10–80, from Spec 08 v1.1)
   - All idempotent (skip if name already exists)

**Breaking change vs old seed:** The old seed had `OCF_SOCIAL_SECURITY` and `FCF_BANK_FEES` which are NOT in Spec 08 v1.1. The new seed does not insert them. If the DB was already seeded with the old taxonomy, those codes may remain but are harmless (movements referencing them will still classify correctly via manual override). For a fresh DB, only v1.1 categories are inserted.

Old intercompany rules also had an `AUTHOR` keyword missing — now included.

## 3. Known Limitations / Future Work

- **Foreign intercompany rules not seeded.** G6 (foreign entity names — Belgium, Colombia, Mexico, Puerto Rico) is still open. Rules for `INT_INTERCOMPANY_FOREIGN` cannot be seeded until the CFO provides entity names/patterns.
- **"AUTHOR" keyword overlap.** The keyword `ISEAZY` matches all IsEazy group entities. If a payment by one entity mentions "ISEAZY" (e.g. an invoice reference), it will be classified as INT_INTERCOMPANY. This requires review against real bank descriptions once the first import runs.
- **Rules not bulk-importable.** There is no CSV/Excel rule import. Rules must be created via API or the UI form one at a time. For large rule sets from the VLOOKUP file, a future import endpoint can be added.
- **No rule test preview.** The UI does not let users test a rule against existing movements before saving. This can be added as a "preview" step in the form.

## 4. How to Verify

```bash
# 1. Start database
docker compose -f infrastructure/docker-compose.dev.yml up -d

# 2. Run migrations
cd backend && alembic upgrade head

# 3. Seed data (companies + taxonomy + rules)
cd backend && python ../scripts/seed.py

# 4. Start backend
uvicorn app.main:app --reload

# 5. Verify taxonomy
curl http://localhost:8000/api/v1/classifications/categories | python -m json.tool

# 6. Verify rules
curl http://localhost:8000/api/v1/classifications/rules | python -m json.tool

# 7. Run batch classification (needs movements in DB first)
curl -X POST http://localhost:8000/api/v1/classifications/batch \
  -H "Content-Type: application/json" \
  -d '{"force_reclassify": false}'

# 8. Start frontend
cd ../frontend && npm run dev
# Navigate to http://localhost:3000/classification
```
