## 1. What Was Done

### Backend — Migration `0002_intercompany_matching`

New migration on top of the initial schema (`backend/migrations/versions/2026_05_11_001_intercompany_matching.py`):

- Adds `IN_TRANSIT` and `UNRESOLVED` to the `match_status` PostgreSQL enum
- Drops `UNIQUE` constraints on `movement_out_id` and `movement_in_id` (a movement can appear in REJECTED matches before being re-matched)
- Makes `movement_in_id` nullable — IN_TRANSIT records have only one known leg
- Makes `company_to_id` nullable — IN_TRANSIT may not know the destination company
- Adds `score NUMERIC(5,4)` — 0.0–1.0 composite match quality
- Adds `transit_expires_at TIMESTAMPTZ` — IN_TRANSIT escalation deadline
- Adds indexes: `idx_intercompany_status`, `idx_intercompany_movement_out`, `idx_intercompany_movement_in`, `idx_intercompany_companies`
- Creates `foreign_entities` table (name, country, known_ibans ARRAY, keyword_patterns ARRAY)

### Backend — Matching Engine (`backend/app/services/intercompany/matcher.py`)

Pure matching logic, no router coupling. `scan_for_matches(db)` runs in three phases:

1. **Escalate** — expired IN_TRANSIT records (past `transit_expires_at`) → UNRESOLVED
2. **Resolve IN_TRANSIT** — for each IN_TRANSIT record, search for the now-imported second leg; if found, upgrade to PROPOSED
3. **Scan new** — iterate all unmatched movements in internal accounts:
   - Pair found (opposite sign, ≤€2 tolerance, ≤3 business days apart) → PROPOSED
   - No pair but counterpart_iban is a known internal IBAN → IN_TRANSIT (5-day window)

Scoring (`_score_match`): 0.4 points for exact amount, 0.4 for date proximity, 0.2 for cross-IBAN identification.

**Constants:**
| Constant | Value | Purpose |
|----------|-------|---------|
| `AMOUNT_TOLERANCE` | €2.00 | Covers bank fee rounding |
| `DATE_TOLERANCE_DAYS` | 3 business days | Match window |
| `TRANSIT_WINDOW_DAYS` | 5 business days | Before escalation |

### Backend — Router (`backend/app/routers/intercompany.py`)

Full implementation replacing the skeleton:

| Method | Path | Purpose |
|--------|------|---------|
| `GET`  | `/api/v1/intercompany/matches` | List matches (filter by status, company, date) |
| `GET`  | `/api/v1/intercompany/matches/{id}` | Single match with embedded movement detail |
| `POST` | `/api/v1/intercompany/matches/{id}/confirm` | Confirm → marks both movements `is_intercompany=TRUE` |
| `POST` | `/api/v1/intercompany/matches/{id}/reject` | Reject with reason → restores movement intercompany state |
| `POST` | `/api/v1/intercompany/matches/manual` | Create manual match |
| `POST` | `/api/v1/intercompany/scan` | Trigger full matching scan |
| `GET`  | `/api/v1/intercompany/summary` | Balance matrix + pending/transit/unresolved counts |
| `GET`  | `/api/v1/intercompany/foreign-entities` | List foreign entity registry |
| `POST` | `/api/v1/intercompany/foreign-entities` | Add foreign entity |

Confirm logic:
- Sets `is_intercompany=TRUE` and `intercompany_match_id` on both movement records
- Prevents confirming IN_TRANSIT (no second leg yet) or already CONFIRMED matches

Reject logic:
- Restores `is_intercompany=FALSE` and clears `intercompany_match_id` if movements were already marked

## 4. Known Limitations / Future Work

- **G6 still open** — Foreign entity names (Belgium, Colombia, Mexico, Puerto Rico) unknown. `foreign_entities` table and registry CRUD are ready; just needs seeding once CFO provides names.
- **G4 resolved by design** — The UI is designed for the CFO to review matches directly (no separate admin role required in Phase 1).
- **`confirmed_by` is hardcoded to "admin"** — Phase 1 has no authentication. Once auth is added (post-Phase 1), this should use the authenticated user's identity.
- **No bulk confirm/reject** — Each match is reviewed one at a time. Can be added as a "Select all + Confirm" feature if the volume warrants it.
- **Foreign entity IBANs for matching** — The `foreign_entities.known_ibans` field is populated in the registry but the matcher does not currently use it for IN_TRANSIT detection (foreign entities are excluded from elimination by design).
